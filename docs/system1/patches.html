system 1 · modular decisions

The patches — one functionality, one patch

Different functionalities need different questions, primitives and thresholds, so each is an independent decision patch. Patches run in a fixed order and hand their accepted decisions to the next via shared context. Adding a capability later = adding a patch — nothing else changes. v1 patches are implemented in the skeleton; candidate patches are proposals, kept open to discuss.

How a patch works

1 · Receiveauto-sectioned sentences (IDs + text) + compact state: known entities, scene-so-far, last speaker
→
2 · Askits own batch of Jev questions — one API call for the whole window, all questions in parallel
→
3 · Interpretprobabilities → accepted decisions, ChangeSet proposals, or escalations (see gates)

The three Jev primitives: noul yes/no → probability  ·  choice one pick from a fixed candidate set  ·  score rating on an ordered scale. Note the design consequence: presence must be one noul per candidate — choice can only ever return a single pick.

The catalog

Order matters

The v1 registry runs: scene-boundary → dialogue-detector → name-detector → presence-detector → speaker-attribution. Speaker attribution needs the present set; presence needs scene spans; the dialogue detector needs nothing but sentences — which is exactly why it goes early. A patch only ever consumes decisions patches before it accepted.
