Rolling by block — and the merge gate

A novel is never ingested in one swallow. Processing rolls chapter by chapter (or by long block), and the System 1 miniloop is never allowed to write to the ontology main graph. It proposes. The main agent decides.

One block, five beats

1 · SECTIONcode splits the block into sentences — stable IDs + offsets
→
2 · MINIloopdecision patches run; every conclusion becomes a proposal
→
3 · EXTRACTwork LLM reads the structured scenes; proposes events + causality
→
4 · ACCUMULATEall proposals collect into one ChangeSet — graph untouched
→
5 · MERGE GATEthe main agent reviews

The three verdicts

APPROVE

Proposals are applied to the main graph through the OntologyStore. The next block rolls.

HOLD

Nothing is applied. Processing pauses; the agent explains why and consults the user.

REVISE

The agent names the parts it doubts; the miniloop re-runs only those parts and returns a revised ChangeSet for the block.

Why an agent behind the gate

The miniloop is fast and local, but it cannot hold what the main agent holds: earlier chapters, naming consistency across a whole book, who a nickname in chapter 30 really belongs to, the user's intent. Making the fast system propose and the context-rich system decide is the core safety property of the design — and it is enforced in code, not by convention: the apply path refuses any ChangeSet whose status is not approved.

ChangeSets double as the audit trail. Every node in the graph can answer: which block, which sentences, which patch, what confidence, whose approval. And when the last block merges, the novel the user asked for is done — the loop has a natural end.
