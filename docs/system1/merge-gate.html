Merge gate — blocks roll, proposals wait, the main agent decides

status: implemented (skeleton) repo: src/merge/ · src/processing/blockProcessor.ts reviewer: the main agent (System 2)

The processing model of the whole system. Ingestion rolls block by block — chapter, or long block. For each block, sectors 01–08 produce proposals; this sector accumulates them into one ChangeSet and holds it at the gate. The main agent — with all its memories and capabilities — reviews: approve the merge, hold it, or ask to revise part of it. Then the next block rolls, until the novel is done.

InputsAll proposals for one block (patches 02–06 + extraction 08), each with confidence + provenance
OutputsApproved ChangeSets applied via OntologyStore (10) — or held / revised ChangeSets with review notes
Depends on07 Miniloop engine, 08 Extraction
Feeds into10 Storage (writes happen only here), then the next block

The three verdicts

APPROVE

Proposals are applied to the main graph through the OntologyStore. The next block rolls.

HOLD

Nothing is applied. Processing pauses; the agent explains why and consults the user.

REVISE

The agent names the parts it doubts; the miniloop re-runs only those parts and returns a revised ChangeSet for the block.

Design details

  • Why an agent behind the gate: the miniloop is fast and local, but it cannot know that a nickname in chapter 30 belongs to a character introduced in chapter 2, or that two similar names are twins. The fast system proposes; the context-rich system decides.
  • Enforced in code, not convention: applyChangeSet refuses any ChangeSet whose status is not approved. There is no other code path from proposals to the store.
  • The audit trail: every proposal carries block ID, sentence IDs, producing patch, and confidence. Every node in the graph can answer: which block, which sentences, which patch, what confidence, whose approval.
  • A natural end: when the last block the user asked for merges, ingestion is done — the loop terminates on the work, not on a timer.

Open questions — the merge gate

  • Revision granularity.When the agent sends a ChangeSet back, what is the unit — a single proposal, a scene, or a patch's whole output for the block? The skeleton re-runs the block; finer units need per-proposal patch provenance to pay off.
  • Review presentation.How should a ChangeSet be summarized for review — counts by kind, lowest-confidence first, new entities spotlighted? The agent reviews faster with the right digest; the user spot-checks with the same view.
  • Auto-approval envelope.Should very high-confidence, low-risk proposal classes (e.g. PRESENT_IN at 0.97) ever skip review in bulk, with the agent auditing samples? Speed vs. the safety property.
  • Cross-block consistency checks.Before approving block N, should the gate run standing queries — duplicate-name suspects, state contradictions — against everything merged so far?
