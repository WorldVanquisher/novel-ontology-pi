Name detector — known, new, and nicknamed

status: v1 patch (skeleton) repo: src/autostep/patches/name-detector.ts model: code scan + Jev · noul / choice

The sector that grows the cast. Its two halves are split by rule zero: code scans the sentences for names and aliases already in the graph — exact, free, certain. Then the decision model judges the leftovers: is this candidate a new name, or a new nickname for someone we already know?

InputsSentences + the graph's alias table (all known name forms) + candidate spans
OutputsCode-scan hits (certain) · proposals: upsert_entity (new character) / add_alias (new nickname) → ChangeSet
Depends on01 Sectioning, 10 Storage (alias table read)
Feeds into05 Presence (candidate cast), 09 Merge gate (its proposals)

Decision questions

is_new_name · noul — Is this candidate a character's name (a person being referred to) that does NOT belong to any already-known character? Places, items and generic nouns ("the teacher") are not character names.
is_nickname_for · choice — If this candidate is a nickname, epithet or title for an already-known character, which one? Options: every known character ID + "none".

Design details

  • Never ask the model what code knows: a string that matches the alias table is a hit, full stop. Jev's context window is spent only on the unknown.
  • Proposals, not writes: a "new character" leaves this sector as an upsert_entity proposal in the block's ChangeSet. The work LLM fleshes the character out during extraction (08); the merge gate (09) decides if they enter the graph.
  • The alias table is the memory: every merged nickname makes future scans cheaper and presence/speaker decisions easier. Names are data on the entity — canonical, alias, nickname, title — in any language.
  • Discovery escalates: a probable new name is important enough to skip the re-ask gate and go straight to careful handling.

Implementation

  • scanKnownNames(ctx) — deterministic scan over ctx.knownEntities name forms; covered by the miniloop test (finds 御坂美琴 with no model call).
  • nameDetector patch — builds the two question types per candidate from ctx.accepted.nameCandidates; interprets answers into proposals / escalations.

Open questions — name detection

  • Candidate generation — the big one.Where do candidate spans come from? Speech-verb patterns (X说道), quote-adjacent sequences, capitalization/CJK heuristics, work-LLM nomination — or a layered mix? This choice drives the sector's recall.
  • Name collisions.Two different people sharing a name (common in long novels, and across generations) — how does the sector know a "known" hit is actually the other person?
  • Cross-language forms.The same character as 美琴 / Misaka / ミサカ — one entity, three surface forms. Who proposes the merge: this sector, extraction, or the main agent at the gate?
  • Titles vs. aliases.Is 姐姐大人 an alias of Mikoto, or an ADDRESSES relation from Kuroko? The schema supports both — the sector needs a rule.
