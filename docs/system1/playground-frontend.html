Playground frontend — the live theater

A standalone web app (React + Reagraph, chosen 2026-10-21) that makes the whole system watchable: as blocks roll through the miniloop, the ontology graph grows on screen in 3D — decisions stream in, proposed changes glow as ghosts, merges land with a pulse. Transparency as a feature: for the user's attention, and for our debugging. Host-agnostic by design — a VS Code webview wrapper can adopt the same component later.

One world: the timeline at chapter range. Down in the branch lane, System 1 is already knitting — ghosts appearing in place.

This single loop is the whole product idea. One world: the ontology graph is the only source of truth; the timeline, the 3D interior and the live feed are cameras over it, never separate data. Two zoom levels: chapter-range big events on the outside; click one and it opens into its 3D interior — character, location, scene, dialogue and event nodes laid out in 3D roughly in chronological order, every link single-directional along an explicit time-flow axis. A story told in two places at once shows two parallel chains (here: the café and the street patrol, interleaved by one phone call). Live, without fighting: while you are inside, the agent keeps knitting in another lane — ghosts appear there, in place, and the activity tab quietly shines. Tap it and a guided flight carries your camera out, across lanes, to the knitting site, arriving as the merge lands.

Design details

  • One graph, many cameras (core principle): live activity and timeline browsing are the SAME surface. Views are cameras/filters over the single ontology graph (the source of truth) — never separate data. The agent's knitting renders in place wherever it belongs (any lane, any chapter, inside any big event) as ghosts, and never moves the user's camera. A follow-agent mode exists, but it is a toggle, off by default.
  • The shining activity tab: agent/System-1 activity elsewhere accumulates as notifications with a location attached (lane, big event, zoom level). The tab glows when something noteworthy lands — new knitting site, a ChangeSet reaching the gate, a merge. Tapping an entry runs a guided flight: the camera travels across lanes and semantic zoom levels to the exact site, expanding containers on the way in. Notification policy is a design knob: merges and gate arrivals always shine; raw verdicts batch silently.
  • Stack: Vite + React + TypeScript; Reagraph (Apache-2.0) for the graph stage — clustering, expand/collapse (chapter → scene → event zoom), node badges for pending proposals; a React Flow strip for the pipeline itself. Both views share selection state: click a block in the strip, the graph flies to what it produced.
  • Event feed is the contract: the CLI emits a typed event stream (block started · sentence sectioned · patch verdict · proposal added · changeset pending · merged · graph rebuilt). The frontend is a pure consumer — first transport is the CLI writing an append-only events.jsonl per novel plus a tiny local SSE server (novel watch); the component never touches the DB directly.
  • Four views, one state: Live Theater (this demo), Ontology Explorer (free 3D browse, search, focus), Timeline Lanes (canon + branches as lanes, scrub/play through event order — DIY over chronologicalOrder), Gate Queue (ChangeSets as cards with diff-style review, approve/hold from the UI).
  • Timeline zoom is semantic, two levels: level 1 shows big events — summarized beats spanning chapter ranges; clicking one expands it into its 3D interior (level 2): characters, locations, scenes, dialogue turns and micro-events laid out in 3D roughly in chronological order along a time-flow axis, single-directional links only. A story narrated in parallel places shows parallel chains — one per location — interleaved only where the narration actually crosses (a phone call, a meeting). Data-wise this is containment: a big event groups scenes/events; zoom = Reagraph expand/collapse over those relations, not a camera trick alone.
  • Ghosts before facts: proposals render as translucent amber ghosts in the graph before approval and solidify on merge — the user literally sees the difference between what the miniloop believes and what is canon.
  • Replay for debugging: the event stream is recorded, so any ingestion run can be replayed step-by-step later (the Agent Flow pattern) — a bug report becomes a rewatchable session.
  • Host-agnostic: no filesystem or VS Code APIs inside the component. A later VS Code extension is a thin shell (webview + the same event feed); the standalone app remains the public face.

Open questions — this sector only

  • Transport final form.SSE from a local server (current plan) vs. WebSocket vs. plain file-tail polling — SSE is simplest and one-directional like the data; bidirectional needs (gate clicks) are ordinary HTTP posts. Confirm SSE?
  • Session recording format.Events already persist as JSONL — how much UI state (camera, selections) joins the recording for faithful replay?
  • Scale guardrails.Reagraph is comfortable in the low thousands of nodes; at whole-novel scale the explorer needs cluster-first rendering (chapters as supernodes) — the default view decision: always clustered, expand on demand?
  • 2D fallback.Reagraph offers 2D layouts in the same component — ship a 2D/3D toggle from day one for weaker GPUs?
  • Notification policy.What earns a shine vs. a silent feed entry — merges and gate arrivals always; escalations (low-confidence, held ChangeSets) immediately? Multiple simultaneous knitting sites: one tab entry per site, or a single rolled-up "3 sites active"?
