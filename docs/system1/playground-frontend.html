Playground frontend — the live theater

A standalone web app (React + Reagraph, chosen 2026-10-21) that makes the whole system watchable: as blocks roll through the miniloop, the ontology graph grows on screen in 3D — decisions stream in, proposed changes glow as ghosts, merges land with a pulse. Transparency as a feature: for the user's attention, and for our debugging. Host-agnostic by design — a VS Code webview wrapper can adopt the same component later.

The timeline has two zoom levels. Level 1 (per chapter range): each node is a big event — a summarized story beat that can span many scenes, strung along the canon timeline. Level 2 (inside a big event): clicking one dives into its internal timeline — the small scenes, dialogue turns and micro-events it contains, drawn as a scene cloud around an inner time axis, every edge arrowed in the direction time flows. Zooming is semantic, not just optical: past a threshold the summary node becomes its contents (Reagraph expand/collapse over the containment relations in the graph).

Design details

  • Stack: Vite + React + TypeScript; Reagraph (Apache-2.0) for the graph stage — clustering, expand/collapse (chapter → scene → event zoom), node badges for pending proposals; a React Flow strip for the pipeline itself. Both views share selection state: click a block in the strip, the graph flies to what it produced.
  • Event feed is the contract: the CLI emits a typed event stream (block started · sentence sectioned · patch verdict · proposal added · changeset pending · merged · graph rebuilt). The frontend is a pure consumer — first transport is the CLI writing an append-only events.jsonl per novel plus a tiny local SSE server (novel watch); the component never touches the DB directly.
  • Four views, one state: Live Theater (this demo), Ontology Explorer (free 3D browse, search, focus), Timeline Lanes (canon + branches as lanes, scrub/play through event order — DIY over chronologicalOrder), Gate Queue (ChangeSets as cards with diff-style review, approve/hold from the UI).
  • Timeline zoom is semantic, two levels (demo 2): level 1 shows big events — summarized beats spanning chapter ranges; clicking one expands it into its internal timeline (level 2): the scenes, dialogue turns and micro-events it contains, in a scene cloud around an inner time axis with directed flow. Data-wise this is containment: a big event groups scenes/events; zoom = Reagraph expand/collapse over those relations, not a camera trick alone.
  • Ghosts before facts: proposals render as translucent amber ghosts in the graph before approval and solidify on merge — the user literally sees the difference between what the miniloop believes and what is canon.
  • Replay for debugging: the event stream is recorded, so any ingestion run can be replayed step-by-step later (the Agent Flow pattern) — a bug report becomes a rewatchable session.
  • Host-agnostic: no filesystem or VS Code APIs inside the component. A later VS Code extension is a thin shell (webview + the same event feed); the standalone app remains the public face.

Open questions — this sector only

  • Transport final form.SSE from a local server (current plan) vs. WebSocket vs. plain file-tail polling — SSE is simplest and one-directional like the data; bidirectional needs (gate clicks) are ordinary HTTP posts. Confirm SSE?
  • Session recording format.Events already persist as JSONL — how much UI state (camera, selections) joins the recording for faithful replay?
  • Scale guardrails.Reagraph is comfortable in the low thousands of nodes; at whole-novel scale the explorer needs cluster-first rendering (chapters as supernodes) — the default view decision: always clustered, expand on demand?
  • 2D fallback.Reagraph offers 2D layouts in the same component — ship a 2D/3D toggle from day one for weaker GPUs?
