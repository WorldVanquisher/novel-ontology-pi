Two layers with distinct jobs: the bundle (plain JSONL files) is the portable source of truth; Ladybug (embedded property graph + Cypher, with native vector and full-text indexes in the same file) is the hot query engine rebuilt from it. Design details

  • Why two layers: the bundle is diffable, git-friendly, shareable by copying a folder, and engine-independent — insurance if Ladybug is ever swapped. Ladybug is a disposable cache: delete graph.lbug, rebuild, same answers.
  • GraphRAG in one engine: a question seeds via vector similarity (event summaries) and FTS (exact names), then Cypher traverses — causal chains, presence, timeline order — from the seeds.
  • Closed schema, designed once: Ladybug requires declared node/relation tables (src/ontology/schema.ts). The English vocabulary is schema v1; new types arrive as CLI migrations.
  • One writer, many readers: only the merge gate writes; queries open read-only. That matches Ladybug's concurrency model exactly — and the CLI's.
  • Retrieval is GRAPH-FIRST (decided 2026-10-21, embeddings deferred): every current need — presence, co-presence, causal chains, scene location, event streams, fork points — is a relational Cypher traversal (src/ontology/retrieval.ts, implemented and tested). No embedding model gets chosen until one of those provably falls short. The fallback design, if that day comes: a lightweight local model on CPU (~500–1000 dims) for wide recall, Jev post-selecting among the top 32 for precision.
  • Vector dimension is manifest data: the embedding model + dimension are recorded per novel; changing models triggers novel graph reindex, not silent corruption.
