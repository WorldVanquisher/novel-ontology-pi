System 1 — The Autostep Miniloop

The fast, local decision system inside the CLI. It reads a novel the way a careful reader skims structure: where scenes break, which sentences are dialogue, whose names appear, who is actually in the room, who is speaking. It decides structure — it never writes the ontology. Everything it concludes becomes a proposal for the main agent to approve at the merge gate.

Rule zero: never ask a model what code can compute exactly. Sectioning, offsets, and scanning for known names are code. The decision model (Jev) is only asked genuinely ambiguous questions — and it answers with probabilities, not text, in ~70–500 ms, batched: one call per window, all questions at once.

3 · The patches — one functionality, one patch

Different functionalities need different questions, primitives and thresholds, so each is an independent decision patch. Patches run in a fixed order and hand their accepted decisions to the next via shared context. Adding a capability later = adding a patch — nothing else changes. v1 patches are in the skeleton; candidate patches are proposals, kept open to discuss.

4 · Confidence gates — the recursion

Every answer comes back as a probability. Deterministic code routes on it, per patch:

‹ 0.55 · escalate — subdivide the window, or hand this unit to the work LLM 0.55–0.85 · re-ask — expand context (previous/next scene), decide again ≥ 0.85 · accept

Thresholds are per-patch and are a tuning topic, not a constant — they get calibrated against real chapters once the Jev test key is wired. The expensive work LLM only ever sees the hard fragments.

5 · Rolling by block — and the merge gate

Processing rolls chapter by chapter (or by long block). Each block's proposals accumulate in its ChangeSet. The main agent — the Pi agent with the full conversation, the memories, earlier chapters, and every other capability — reviews it:

APPROVE

Proposals are applied to the main graph through the OntologyStore. The next block rolls.

HOLD

Nothing is applied. Processing pauses; the agent explains why and consults the user.

REVISE

The agent names the parts it doubts; the miniloop re-runs only those parts and returns a revised ChangeSet for the block.

Why an agent behind the gate: the miniloop is fast and local, but it cannot know that a nickname in chapter 30 belongs to a character introduced in chapter 2, or that two similar names are actually twins. The fast system proposes; the context-rich system decides. Every ChangeSet is also the audit trail — each node in the graph can answer: which block, which sentences, which patch, what confidence, who approved.

6 · Open questions — to plan together

  • The patch catalog itself.Which candidate patches (§3) earn a v1 slot? What functionality is missing entirely?
  • Name-candidate generation.How does the name detector propose candidate spans for new names — speech-verb patterns, quote-adjacent sequences, work-LLM nomination, or a mix?
  • Revision granularity at the merge gate.When the main agent sends a ChangeSet back, is the unit of revision a single proposal, a scene, or a patch's whole output for the block?
  • Gate thresholds per patch.Accept / re-ask / escalate cut-offs (0.85 / 0.55 proposed) — to tune with the Jev test key on a golden chapter.
  • Window sizing.How many sentences per window, and how much scene context rides along as state, given Jev's ~32k-token context?
  • Simulation-side reuse.The same Jev connector can gate roleplay later (in-character checks, fork suggestions, branch matching) — designed now or later?
